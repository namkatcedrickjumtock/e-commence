02
The thesis

Your error handling is probably lying to you

  • Over-wrapping error messages
  • Letting your database leak into your business logic
  • Reinterpreting errors so the wrong HTTP status fires
  • Exposing your provider's internals to every client

The problem

Errors don't stay where they start

Amplified

Misinterpreted

Leaked

Every layer between the error and the client can change what the error means — and whether the client gets the right response at all.

06
The map

4 patterns that break layered systems

1
Excessive Wrapping
Every layer stamps its own signature.
2
Abstraction Leakage
Errors from one layer bleed into another.
3
Meaning Reinterpretation
Errors get relabeled, firing the wrong status code.
4
External Provider Leakage
An external system's error contract bleeds into yours.

Every one of these came from production. The demo app reproduces them on purpose.

09
Anti-pattern 1 · the lesson

Signal vs. noise

noise

Every layer's name, retyped by hand. You already have a call stack for that.

signal

The route that was called. The root cause at the bottom.

persistence:  "repository: GetOrder query failed: ... not found in database: %w"
↓
services:     "service layer: failed to retrieve order details: %w"
↓
api:         "handler: GET /orders/{id} failed: %w"

Adding context is good. Adding every layer's name is noise.

13
Anti-pattern 3 · the lesson

A status code is a promise

persistence:  sql.ErrNoRows            ← "product not found"
↓
services:     "stock data unavailable: %w"  ← relabeled!
↓
api writeError: Contains(msg, "unavailable") → 503  ← matches first
                Contains(msg, "no rows") → 404     ← never reached

The mapping became order-dependent and fragile. A layer may enrich an error — never change its category.

15
Anti-pattern 4 · the lesson

Translate at the boundary

what leakedStripeError
RequestID:   "req_7NdM..." ← trace id
Type:       "card_error" ← category
Code:       "card_declined"
DeclineCode: "insufficient_funds"
ChargeID:   "ch_3RJX..." ← charge ref
Message:    "...insufficient funds."
persistence — the fixv0.2
func (p *StripeProvider) Charge(...) error {
  err := stripe.Charge(ctx, amount)
  if isDeclined(err) {
    return &PaymentError{
      Code: "payment_declined",
      Retryable: false,
    }
  }
}

StripeError never leaves the persistence package. It becomes a domain type your clients can depend on.

16
The principle

Errors are architecture

Presentationinvalid request · malformed payload · bad paramsowns
Domainbusiness rule failures · domain invariantsowns
Infrastructuredatabase failures · external system failuresowns

The layer where an error originates defines its meaning. Propagate upward unchanged. Translate only at boundaries.

17
Before · after

Same codebase. Different discipline.

services — relabels & wrapsv0.1
func (s *service) GetProduct(...) {
  p, err := s.repo.Get(ctx, id)
  if errors.Is(err, sql.ErrNoRows) {
    return fmt.Errorf("service: product
    not found in database catalog: %w", err)
  }
}
translate · propagate · map by typev0.2
// persistence — translate at the boundary
if errors.Is(err, sql.ErrNoRows) {
  return ErrProductNotFound
}
// services — no db imports, no wrapping
return err  // propagate unchanged
// api — centralized errors.Is mapping
case errors.Is(err, ErrProductNotFound): 404

The database driver never leaves persistence. writeError maps typed sentinels, not strings.

18
What changed?

What actually changed?

Before — v0.1After — v0.2
database/sql imported in business logic→no infrastructure imports in services
sql.ErrNoRows propagates raw to HTTP→translated to ErrProductNotFound at the boundary
service relabels "not found" as "unavailable"→"not found" stays "not found" through all layers
strings.Contains matching in writeError→errors.Is on typed sentinels
StripeError leaks to client→translated to PaymentError at the boundary

Same stack. Same endpoints. Same database. Only the error discipline changed.
